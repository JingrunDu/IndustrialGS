# 动态更新测试

两次测试各使用一张 H20，默认队列 `embodied_ai_h20_na130`。
分别恢复第一次和第二次建模训练的 665,000 步完整训练断点，
使用相同的 6,650 张图片，再训练 332,500 步，累计停止于 997,500 步。
进度条、loss CSV及W&B横轴使用本次更新步数1至332,500；
CSV另存cumulative_iteration记录内部累计步数。loss仍每100步记录一次。
保持原训练参数和学习率调度，不重新开始训练或重新增密。
使用原有图片的方案测试动态更新训练耗时，不验证新增场景变化。

## 提交两次测试

```bash
cd /home/dujingrun.djr/code/huanliufa_bushu
python3 third_party_test/submit_dynamic_update.py --submit
```

提交两个独立的单 GPU 任务，可并行运行。沿用现有的 OSS 和 W&B 认证；
W&B 继续只记录 loss。需要离线记录时在命令前设置 `WANDB_MODE=offline`。

## 输出及计时

每次提交使用独立的新目录，原始模型和断点不变：

```text
oss://fmc/beifen/data/3dgs_bushu/dynamic_update/<运行日期时间>/test1/
oss://fmc/beifen/data/3dgs_bushu/dynamic_update/<运行日期时间>/test2/
```

- `dynamic_update_plan.json`：起始断点、数据量和训练预算。
- `dynamic_update_result.json`：实际新增步数、本次 Training time、高斯数及是否满足 3 小时。
- `train.log`、`runtime.json`、`loss_log.csv`：训练日志、进程耗时和 loss。
- `point_cloud/iteration_997500/`、`checkpoints/`：更新模型及可恢复断点。
- `visualization/index.html`：12组实拍图、更新前和更新后渲染图对比。

Training time 在每次训练进程中从零累计，断点不保存历史时间，
所以直接取本次日志的数值，无需再扣除原建模训练时间。
runtime.json 的进程墙钟时间作为辅助记录；渲染在计时结束后执行。
训练未完成 332,500 步、提前触发资源保护或异常退出时，不判为达标。
继承的原实验预算仍为 1,995,000 步，因此正常完成本测试时训练状态
可以是 `paused_stage`；以实际累计 997,500 步和新增 332,500 步判定完成。
